# Text replacement lists come and go as text, CSV and JSON

Cited as D-L85.

The text replacement list (D-L84) is imported from, and exported to, three file formats, read and written in one module, `core/model/autocorrect-import.js`. Each carries how a replacement fires as D-L91 says: JSON and CSV as `fires`, and QMK's text not at all for one that fires after the Leader key alone, said in its first lines:

- **JSON**, Ark's own: `{"version": 1, "replacements": [{"replacement": "because", "inputs": ["becuase", "recieve*"]}, {"macro": 5, "inputs": ["sig"]}]}`. An input is written as the screen writes it, with `*` where other letters may go (D-L84), and a replacement that plays a macro names its slot in place of its text. A file in another version is refused whole.
- **CSV**, for a spreadsheet: columns `replacement` and `inputs` under a header row, in any order. The inputs cell may hold several inputs with spaces between them, since one never holds a space, each with its own `*`. A list with a replacement that plays a macro has a third column, `macro`, holding the slot, with the replacement cell empty. Ark reads what Excel, Numbers and Google Sheets save: RFC 4180 quoting, a comma or a semicolon between cells (the one the first row has more of, since a European spreadsheet saves semicolons), a byte order mark, rows padded with empty cells at the end. Ark writes a byte order mark (without one Excel on Windows reads the file in the system's code page and mangles accents), the header row, commas, and a row for each replacement, so the file opens one replacement a row. A spreadsheet may still retype a cell (a leading zero, a leading `+` or `=`); the guide says so.
- **Text**, QMK's autocorrect dictionary: `typo -> correction` a line, `#` comments and blank lines skipped. It is what people who used QMK's autocorrect already have. QMK writes where a typo matches with colons, the same four matches Ark writes with `*`: `:x:` is `x`, `:x` is `x*`, `x:` is `*x`, and `x` with no colons is `*x*`. Nothing changes meaning either way. The format has no way to say a macro: Export leaves such replacements out and says how many in a comment on the file's first line, and Import also reads the firmware's own authored form of one, `:typo: => slot`.

Files written before these names are still read: a JSON list of `entries` with `correction` and `typos`, each a `{"typo": …, "match": "whole word" | "start" | "end" | "anywhere"}`; a spreadsheet with `typos`, `correction` and an optional `match` column, and one with no header row at all, read as those columns in that order. A `match` stands for an input written without `*`; a `*` the form is written with says where it matches whatever the column says. So a list exported by an earlier Ark, and a QMK-style list, import as the same list.

In every format, lines and rows with the same replacement, spelled exactly alike, are one entry, so a file can give one replacement many inputs however it lists them. A list exported as JSON or CSV imports as the same list; one exported as text does too when no replacement plays a macro. A macro is named by its slot, so a list with one belongs to the profile whose macros it names.

A file is untrusted and never trusted to be well formed. A line Ark cannot read (no arrow, a wrong number of columns, an unknown match, an empty cell, a macro that is no number) is refused with its line, row or entry number and the reason, and the rest is read. Only a file that is not a list at all is refused whole: over 262,144 bytes, not JSON under a `.json` name, or another version.

Nothing changes on import until the owner chooses. Core reads the file against the draft and answers with a preview of both choices, **Add to my list** and **Replace my list**: the replacements it would make, what it would add to replacements the list has, what is already there (skipped), the lines refused, the file's and the list editor's own (D-L84) in the file's order, and how many inputs do not fit, with what stopped the first of them. Fitting is judged by everything an edit is refused for: the two counts, the text, the domain's own bytes and the room left in the profile, so a choice the sheet offers is never refused whole as profile full. In Add, an input the list already has for another replacement is refused and named, never moved. The choice is then one draft edit carrying the preview's entries, which core plans again as it applies it, so what is kept is what the list takes at that moment and one undo takes it back.

Export writes the draft's list, the edits not yet saved included: it is what the screen shows.

## Considered options

JSON only: a list could not be brought from QMK or edited in a spreadsheet. A `match` column or field beside each input, as the first format had: a second way to say what the `*` says, which a hand-edited file could set against it. CSV with one input a row, as the text format has: the replacement would be written once per input, against D-L84, and Ark still reads such a file, since rows with one replacement merge. Writing a macro by its name: names change and need not be unique. Refusing to export a list with a macro replacement as text: most of such a list is still worth having in QMK's format, and the file says what it lacks. Guessing a wrong column count or an unknown match: a spreadsheet saved with the wrong separator would import as nonsense; a refusal with its row number says what to fix. Importing straight into the draft and leaving the owner to Review: a file's refused lines and what did not fit have nowhere to be said in Review, which compares the draft with the keyboard. Copying an existing typo list for a starter list: Ark is GPL-2.0, and the lists in common use are under licences it cannot take text from, so Ark wrote its own, and has since stopped shipping one (D-L90).
