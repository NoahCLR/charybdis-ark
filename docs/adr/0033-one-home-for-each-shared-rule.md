# One home for each rule the app needs twice

Cited as D-L33.

Every rule the app needs in more than one place has one owning module, and the core publishes its meaning to the interface; screens do not rebuild vocabulary, device policy or draft state. Duplicated knowledge drifted: the same stored value got different words in review and screens, the pointing keycode registry existed in several copies, a draft was decoded many times per publish, and the shell sequenced Apply itself. The owners are listed in [Interface rendering and rule ownership](../spec/interface-contracts.md#shared-rule-ownership).

Amended 2026-10-28 (D-L73): a firmware decision that depends only on the profile is published as a fact, and the interface interprets only published data. A rule the page runs as a person clicks has its one home in `rules/`, which core and the interface both import.
