# Core publishes firmware decisions, and the rules both sides run live in `rules/`

Cited as D-L73.

A firmware decision that depends only on the profile is computed in core and published in the model, and the interface reads what is published instead of working the decision out again. A firmware rule that the interface works out beside core has two homes that can drift, and an interface that holds one cannot be replaced without rebuilding it. Which stack slots answer each position (each layer's `answers`, `core/model/layer-resolution.js`), the layers that start a pointing mode with, for each, the layers whose being on ends that start (`pdModes[].linkStarts`, `core/model/pointing-links.js`), and the layers each keycode turns on (`qmkKeyTurnsOn`, `core/model/layer-reach.js`) are published this way. This refines D-L33. Noah's call, 2026-10-28.

A firmware rule the page has to run as a person clicks, because its answer depends on the layers a person turns on, lives once in `rules/`, reads what core publishes, and is imported by core and the interface both. Three rules are of this kind: the answer match, which compiled answer a position gives under the layers turned on together with ⌘/Ctrl-click in the layer bar; the link-start check, whether a published link start holds under the layers that are on; and the lighting colour compositor, which is a firmware rule, not presentation. The answer match is `rules/layer-answers.mjs`. A rule is a synchronous ES module. It imports only `rules/` and uses no DOM and no Node. It takes primitives (masks, index arrays, plain records), never a decoded profile or the posted model. Core loads it with `require()` (Node's `require(esm)`), the interface imports it by relative path, and the web build bundles it into both. In core, the layers from `schema/` up may run a rule. `data/` is inert, and `transport/` moves bytes without knowing what they mean. In the interface only `webview/view/` may: it turns the model into what is drawn, purely and under test. The store, screens and DOM helpers reach a rule through it, and the shell runs none. This amends D-L10: the webview still imports nothing from `core/`, only from `rules/`. `tests/layering.test.js` and `tsconfig.rules.json` hold it.

## Considered options

Publishing every answer from core, with no shared code: rejected for the interactive rules. Sixteen layers give tens of thousands of combinations a person can turn on, too many to publish. Letting the webview import core's modules: rejected, because core is CommonJS written against the decoded profile, and the interface would be tied to its internals. Copying a rule into the interface and pinning the copy with a drift test: rejected, because a copy is a second home that drifts.
