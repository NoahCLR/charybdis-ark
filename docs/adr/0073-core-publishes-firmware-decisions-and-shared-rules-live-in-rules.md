# Core publishes firmware decisions, and the rules both sides run live in `rules/`

Cited as D-L73.

The interface re-derived firmware rules that core also computes: which layer answers a key, whether a behaviour or a combo runs on a layer, how a combo forms, reach, the built-in hold rule and the lighting colour compositor. Each of those had two homes that could drift, and the interface could not be replaced without rebuilding them. So core publishes every firmware decision that depends only on the profile as a fact in the model: participation decisions, combo and reach facts per layer, the LED map, the always-on layer mask and the built-in hold rule. The interface interprets only published data. Why a behaviour or a combo does not run reaches it as a code, with its words in `core/model/vocabulary.js`. This refines D-L33. Noah's call, 2026-10-28.

Some rules have to run in the page as a person clicks: which layer answers under the layers turned on together with ⌘/Ctrl-click in the layer bar, the pointing link-start check, and the lighting colour compositor, which is a firmware rule, not presentation. Each of these has one implementation in `rules/`, which core and the interface both import. A rule is a synchronous ES module. It imports only `rules/` and uses no DOM and no Node. It takes primitives (masks, index arrays, plain records), never a decoded profile or the posted model. Core loads it with `require()` (Node's `require(esm)`), the interface imports it by relative path, and the web build bundles it into both. In core, the layers from `schema/` up may run a rule. `data/` is inert, and `transport/` moves bytes without knowing what they mean. In the interface only `webview/view/` may: it turns the model into what is drawn, purely and under test. The store, screens and DOM helpers reach a rule through it, and the shell runs none. This amends D-L10: the webview still imports nothing from `core/`, only from `rules/`. `tests/layering.test.js` and `tsconfig.rules.json` hold it. The first rule is the answer match, `rules/layer-answers.mjs`.

The interface's own guess that layer 0 is the default layer (`webview/view/layer-resolution.mjs`) is a firmware decision it should not make. It goes once core publishes the always-on layer mask, in a change of its own that people will see.

## Considered options

Publishing every answer from core, with no shared code: rejected for the interactive rules. Sixteen layers give tens of thousands of combinations a person can turn on, too many to publish. Letting the webview import core's modules: rejected, because core is CommonJS written against the decoded profile, and the interface would be tied to its internals. Copying a rule into the interface and pinning the copy with a drift test: rejected, because the copies were the problem.
